# Pride Toyota — Delivery Dashboard

A private, auto-syncing dashboard for tracking vehicle delivery/inventory
status at Pride Toyota (Goyal Sons Automobiles Pvt. Ltd.), sourced live from
a SharePoint-hosted Excel workbook via Microsoft Graph.

Dark-mode, Toyota-red accented, HUD-style UI: dynamic KPI cards, a full
filter panel (status multi-selects + 4 independent date-range filters),
and a sortable/searchable/paginated table over the full column set.

## Live sync status

Until Azure AD credentials are added (see [SETUP.md](./SETUP.md)), the
dashboard runs against a bundled realistic mock dataset
(`public/data.json`, generated by `scripts/generate-mock-data.mjs`) so it's
fully functional and demoable. Once credentials are added as GitHub
secrets, `.github/workflows/sync.yml` starts overwriting `public/data.json`
with real data from the workbook every 30 minutes.

## Architecture

```
scripts/
  dateParser.mjs           Excel-serial + locale-text date parsing (the
                            single source of truth for date correctness)
  test-date-parser.mjs     Standalone test proving serial vs. text dates
                            for the same calendar date converge — run with
                            `node scripts/test-date-parser.mjs`
  sync.mjs                 Client-credentials Graph auth → resolve shared
                            file → read table/usedRange → normalize columns
                            → write public/data.json → commit if changed
  generate-mock-data.mjs   Produces a realistic public/data.json for demo
                            use before Azure credentials exist

src/
  types.ts                 Fixed internal VehicleRow schema
  config/access.ts         SHA-256 hash for the soft passcode gate
  lib/
    dataLoader.ts           fetch()'s public/data.json
    filterLogic.ts           All filter/sort/search logic, pure functions
  components/
    AccessGate.tsx          Passcode screen (see Security caveat below)
    KpiRow.tsx               Dynamic per-status KPI cards
    FilterPanel.tsx          CTDMS/Customer status multi-selects + date ranges
    MultiSelect.tsx / DateRangeField.tsx   Reusable filter controls
    VehicleTable.tsx         Sortable, per-column-filterable, paginated table
  App.tsx                   Wires it all together; loading/error states

.github/workflows/
  sync.yml                  Cron (every 30 min) + manual trigger: runs
                             sync.mjs with secrets injected as env vars
  deploy.yml                On push to main: build + deploy to GitHub Pages
```

### Data flow

```
SharePoint Excel workbook
        │  (Microsoft Graph, client-credentials auth)
        ▼
scripts/sync.mjs  ──►  public/data.json  { generatedAt, rows[] }
        │
        ▼
  React app fetches data.json client-side, all filtering/sorting/
  pagination happens in the browser (no backend at runtime).
```

### Why KPI cards and status filter options are never hardcoded

CTDMS Status and Customer Status values are whatever distinct strings
actually appear in the live sheet — the code never assumes a fixed list.
`src/lib/filterLogic.ts`'s `distinctValues()` derives every KPI card and
every multi-select/dropdown option directly from the loaded dataset.

### Date correctness (top priority)

Graph's `usedRange(valuesOnly=false)` response gives three parallel grids
for every cell: `values` (raw — often an Excel serial number, sometimes
already a string), `text` (always the displayed string), and
`numberFormat` (the Excel format code). `scripts/dateParser.mjs`:

1. If the format code looks like a date and the raw value is numeric →
   converts the Excel serial number (epoch `1899-12-30`) to `YYYY-MM-DD`.
2. Otherwise tries explicit `DD-MM-YYYY`, `DD/MM/YYYY`, and ISO text
   parsing against the displayed text.
3. Blank/unparseable → `null`, never a fabricated date.

Verified explicitly — run:

```bash
node scripts/test-date-parser.mjs
```

This proves an Excel-serial-origin date and a text-formatted date for the
*same calendar day* produce the *identical* ISO output.

## Local development

```bash
npm install
npm run dev       # http://localhost:5173, runs against public/data.json
npm run build      # production build → dist/
```

Default access passcode for the local/demo build: **`pridetoyota2026`**
(see "Security caveat" below on how to change it).

## Wiring up live sync

See [SETUP.md](./SETUP.md) for the full Azure AD app-registration walkthrough.
Short version: register a client-credentials app, grant it Graph
`Sites.Read.All` (application permission, admin-consented), then add
`AZURE_TENANT_ID` / `AZURE_CLIENT_ID` / `AZURE_CLIENT_SECRET` /
`SHAREPOINT_SHARE_URL` as GitHub Actions repo secrets. Locally, copy
`.env.example` to `.env.local` and run:

```bash
node --env-file=.env.local scripts/sync.mjs
```

## Deployment

Push to `main` → `.github/workflows/deploy.yml` builds the Vite app and
deploys `dist/` to GitHub Pages (Pages configured to build from GitHub
Actions). `.github/workflows/sync.yml` runs independently on a 30-minute
cron and commits `public/data.json` whenever it changes; a push from that
commit re-triggers the deploy workflow, so the live site stays in sync
automatically.

## Security caveat — read this before treating the passcode as real security

The `AccessGate` passcode screen (`src/components/AccessGate.tsx`,
`src/config/access.ts`) is a **soft deterrent only, not real access
control**. GitHub Pages serves the built `dist/` bundle publicly over the
internet — that's true *regardless of whether the source GitHub repo is
private* — so:

- Anyone with the Pages URL can open browser devtools, read the passcode
  hash out of the shipped JS bundle, and brute-force or simply read past
  it. SHA-256 hashing the passcode client-side stops a casual glance at
  the source, not a determined visitor.
- `public/data.json` itself is a static file at a predictable URL — it is
  fetchable directly, bypassing the passcode screen entirely.

This gate exists only to keep the dashboard out of search engines and
prevent someone who stumbles on the link from immediately seeing dealer
data. **If real access control is needed** (auth that actually keeps
unauthorized users out, including of the raw JSON), the site needs to move
off static GitHub Pages hosting to something with a real backend/auth
layer — e.g. a Vercel/Netlify deployment behind SSO or Basic Auth, or an
Azure Static Web App with Entra ID authentication. Ask if you'd like this
set up.

To change the passcode, see the instructions at the top of
`src/config/access.ts`.
